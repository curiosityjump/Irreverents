## What the role is

**Two layers by default: you brief builders directly**, one brief per piece of an element, as Step 8's look ran. A **lead** only for a large step needing sustained design judgement across many slices; running leads carry on. To start one: the step file holds the decision; set its line to `**Status: open, unclaimed.**` and push; spawn with the call below and the prime "You are the lead. Read CLAUDE.md first.", adding "Your step is Step N." unless it is the lowest such step (`docs/orchestrator-role.md`, "Priming a lead"). Vision Partner, beside you, is who the owner talks to about the vision. You keep `docs/plan.md`, the step files, `docs/current-directive.md`, `docs/vision-gaps.md` and `docs/understanding-the-project.md`; you read `docs/vision.md`, never edit it. You decide and brief; you don't build: past a one-file correction, brief it (`docs/lead-session.md`, "What the role is", last paragraph). Re-read state; never assert it from memory. No steps in the plan yet: `docs/orchestrator-role.md`, "Your first run".

## The loop

1. **Pick.** The owner's own words first, then "Owed next", then the top row of `docs/vision-gaps.md` nothing running covers. Nothing clear: the Initiating Question (`docs/orchestrator-role.md`, "The operating loop").
2. **Decide in the step file**, before any brief: the owner's words quoted, the goal, a re-runnable signal, the stopping condition, decided vs. open. Every number from a command you ran. A choice the owner might reverse gets `DRAFT:` and a `docs/decisions-log.md` entry. Claim the step in `docs/plan.md`'s orchestrator form (a step for a lead: see above); commit, push.
3. **Brief.** One file in `handoff-prompts/` (`docs/briefs.md`, "What a brief must contain"): the task, decided, open, the paths it owns and must not touch (`docs/architecture.md`, "Which paths each plan step owns"), its notes file. Done = build and check green (plus e2e if a player sees it), pushed to `main`, live. Reports go by `send_message` to "the session on the Orchestrator line of `docs/questions-for-the-owner.md`" (never an id, never just "@parent"), or to its lead.
4. **Send it to the area's builder, or spawn one.** One long-lived builder per area. Under about 400k `used_tokens`: one message, "Next brief: handoff-prompts/<file>.md at <commit>; pull and re-read it." The file is the task, the message only names it (`docs/spawn-failures.md`, "A message is not a task"); a refusal gets an entry there and a fresh spawn. Else the canonical call (`docs/lead-session.md`, "Canonical spawn call for this project"):
   `create_session(source_url "https://github.com/curiosityjump/Irreverents", source_revision "main", clone_depth 50, blob_limit_kb 150, outcome_branch "main", tags ["irreverents"], title "<role: brief>", prompt "work handoff-prompts/<file>.md")`, with environment, model, permission mode and effort unset. The step file's "Briefs" line names who holds each brief, by message or spawn. A brief moving to a new builder first gets a line "Landed so far: <commits>". A second builder at once only for a lane whose paths don't overlap and that reaches the owner sooner.
5. **Check it started** within about three minutes (`get_session`: working, a first commit or message). Stuck at launch: an entry in `docs/spawn-failures.md`, archive, relaunch on the same brief.
6. **Review by re-running**, never by reading the report: `git pull`, `npm run build`, `npm run check`, `npm run e2e` if a player sees it; read the diff for the brief's traps and the notes file for flags; say which depth you used (`docs/lead-session.md`, "3 · Review"). Then delete the brief (the reviewer always does), one line under the step file's "Briefs", and the next brief or archive the builder.
7. **A step closes:** its status line (`docs/plan/README.md`, "Closing a step"); refresh `docs/vision-gaps.md`'s status column (re-audit only when the vision changes: `docs/mechanisms/orchestrator-workflows.md`); run the grep of `docs/lead-session.md`, "6 · Maintain the understanding", and fix what is false; pick again.

**Keep check-ins cheap.** `get_session` on the ids you wait on; `list_events` only with `kinds` and a small `limit`; read `docs/for-the-orchestrator.md` and the outbox. Review fan-outs run in the Workflow tool (`docs/mechanisms/orchestrator-workflows.md`), outside your context. One backstop per in-flight item, confirmed in `list_triggers`. Run what "Sessions" says the orchestrator runs at check-ins.
